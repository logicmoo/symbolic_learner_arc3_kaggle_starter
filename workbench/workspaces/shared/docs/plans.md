# Planning Strategies and Executable Plans

[Back to repository README](../../../../README.md)

The workbench uses **Workflow** for the executable artifact that a PDDL expert would call a **plan**. A Workflow may be authored by a human, emitted by a PDDL planner, generated by an LLM, or assembled from nested Workflows. Its steps are grounded or partially bound occurrences of Operations.

The resources historically serialized as `plan` and `plan_variant` are **Planning Strategies**. They do not represent PDDL plans. They describe how a planner should select, generate, constrain, or adapt a Workflow. The legacy kind names remain readable for workspace compatibility.

## PDDL correspondence

| PDDL concept | Workbench concept |
|---|---|
| Domain action schema | Operation |
| Ground action | Workflow step |
| Domain/problem goal | Goal plus AtomSpace bindings |
| Planner configuration or method | Planning Strategy |
| Plan | Workflow |
| Plan execution trace | Workflow Run, Events, States, and Logs |

## Filesystem convention

- Strategy specifications and alternatives may share `plans/<id>.plan.metta`.
- Separate alternatives may use `plan_variants/<id>.<name>.plan_variant.metta`.
- Every alternative declares `parents`; the strategy lists the alternative in `children`.
- A strategy variant may select an existing Workflow or configure a planner that produces one.
- `preferredChild` identifies the preferred strategy variant.

Shared strategies are inherited by project workspaces. Workspace resources with the same semantic ID override Shared records.

## Execution boundary

A Goal Run resolves a Goal, Planning Strategy, optional AtomSpace bindings, and a Workflow. The Workflow is the common executable representation whether its provenance says `human`, `pddl`, `llm`, or another planner. Runtime records preserve the resolved strategy and Workflow without rewriting either design resource.
